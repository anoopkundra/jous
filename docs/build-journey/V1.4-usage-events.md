# V1.4B — Immutable Normalized UsageEvent

## Scope and status

V1.4B implements the first additive edge in the accepted V1.4 chain:

```text
RouteDecision → terminal Execution outcome → UsageEvent
```

The UsageEvent is normalized immutable evidence about usage carried by the
already-persisted V1.2 Execution. It is not a charge, cost, supplier invoice,
receipt, ledger posting, proof of collection, customer acceptance, or credible
task completion. No unavailable values are synthesized and no money is
calculated.

V1.4B does not implement EconomicReceipt, ledger or balances, Project Economics,
customer charges, savings, rewards, reconciliation, payment rails, new provider
activation, retries, fallbacks, or multi-attempt execution. No public usage
mutation endpoint was added.

## Identity and normalization

`jous_api.usage_events.normalize_execution` is the only current normalizer. Its
version is `jous.execution-usage.v1`; its source type is `execution_usage`.
`source_revision` is the stable literal `execution-row-v1`, identifying the
immutable, terminal, unique V1.2 Execution row as the source. The canonical
evidence digest binds the selected source values and normalized usage. The
deterministic UsageEvent UUID is UUIDv5 over execution ID, normalizer version,
and source revision. The database uniqueness key is
`(execution_id, normalizer_version, source_revision)`.

Canonical payload bytes use UTF-8 JSON with sorted keys, compact separators,
explicit `null`, and no NaN. The SHA256 covers those exact bytes. It includes a
payload schema version, tenant/task/claim/execution binding, optional route
decision, source identity, usage status and dimensions, observation time,
normalizer version, and predecessor ID. It excludes database `recorded_at` so
replay remains deterministic. PostgreSQL verifies the digest and that the
payload’s typed values match the stored columns.

The normalizer preserves the five dimensions present in V1.2 evidence:
`input_tokens`, `output_tokens`, `total_tokens`, `cached_input_tokens`, and
`reasoning_tokens`. Values must be nonnegative integers. A normalizer-versioned
AVAILABLE event requires input, output, and total tokens; it preserves the
reported total and does not infer it by summation. PARTIAL preserves only the
present dimensions. UNAVAILABLE stores all dimensions as SQL NULL. Missing
cached or reasoning usage is never changed to zero.

## Source binding and decision boundary

The persisted event binds organization, project, actor, task, dispatch claim,
and execution. A composite foreign key binds it to the immutable task claim;
the source execution and RLS checks require that same tuple. If a persisted V1.3
RouteDecision exists for the task, the application binds its exact decision,
logical-model version, selected route, and route version. The database INSERT
policy requires a matching decision and rejects an event that omits one. If no
RouteDecision exists, the event remains a legacy-bound event with a NULL
decision ID and version fields; no decision is fabricated. The estimated V1.3
route cost is not copied into UsageEvent and is not treated as usage cost.

V1.2’s one terminal Execution per task/dispatch claim remains unchanged.
Unknown/finalization-gap behavior is unchanged. A terminal `unknown`, refusal,
known error, or not-dispatched outcome can produce an UNAVAILABLE event only
when that source Execution explicitly says usage is unavailable; the event
records no token counts in that case.

## Persistence, replay, and correction

`SQLUnit.finalize` writes Execution and its normalized UsageEvent in the same
database transaction. If either insert fails or the process loses the commit
result, transaction rollback or replay cannot leave two canonical events. An
exact replay resolves to the existing event only when its identity and digest
match; a collision fails closed. No provider work is retried as part of
normalization.

Corrections are linear and append-only. A correction uses a new normalizer
version and points to the predecessor. The unique predecessor constraint allows
at most one direct successor. There is no mutable current flag; the latest event
is derived by following the chain. V1.4B does not accept supplier reconciliation
or disputes.

## Persistence and security

Migration `0007_usage_events` is the single linear successor to
`0006_snapshot_binding` and creates only `public.usage_events`, its index,
constraints, RLS, and grants. RLS is ENABLED and FORCED. PostgreSQL role
`postgres` owns the table. `jous_runtime` receives column-level SELECT and
INSERT except the database-generated `recorded_at`; it receives no UPDATE,
DELETE, TRUNCATE, or REFERENCES authority. `jous_security_reader` and PUBLIC
receive no table authority. RLS binds reads and inserts through the existing
task/execution/organization-membership contracts. The INSERT policy compares
all normalized dimensions and status to the persisted Execution usage JSON,
requires source revision `execution-row-v1`, and requires a matching persisted
RouteDecision whenever one exists, preventing direct runtime inserts from
inventing or omitting source evidence. No SECURITY DEFINER function
or reconciliation role was added.

The ordinary V1.2/default and V1.3 relation profiles remain closed to
`usage_events`; only a separate exact V1.4 successor profile admits that one
relation and revision `0007_usage_events`. The product app now requires the
current 0007 profile before accepting traffic. This is a local code/migration
contract only: managed migration and rollout are not authorized by this step.

transaction, tenant, replay, and runtime-authority boundaries only. Managed
migration, managed catalog/security certification, customer-readable usage
projection, and all downstream economic objects require separate authorization.
