# Jous V1.3A — Pricing and Route Authority

Status: contract/schema candidate for CTO review. This is a non-dispatching
authority slice. It adds no migration, API integration, provider call, or route
activation. V1.1 and V1.2 remain frozen.

## Product boundary and current execution seam

Jous owns logical-model, route, pricing, eligibility, effective-cost,
ranking, selection, rationale, and durable economic-decision authority.
Supplier adapters and gateways own provider-protocol translation, credentials
on the server side, transport, and normalized execution evidence only.

V1.2 already supplies the seam to extend: `ExecutionService` receives an
injected adapter; `jous_supply.contracts` defines `ExecutionRequest`, bounded
`Outcome`, and safe route-unavailable errors; `registry.py` contains the
source-owned route; `token_budget.py` performs a hashed local Qwen tokenizer
count; the task store commits a dispatch claim before I/O; provider I/O occurs
outside the database unit; and a new authorized unit finalizes the outcome.
V1.2 deliberately does not retry or redispatch ambiguous provider outcomes.

The current task request includes a caller-supplied `route_id`. V1.2 resolves
that against the single source-owned route and denies real Hugging Face
dispatch before writing a task claim because
`HOSTED_TOKEN_TEMPLATE_AUTHORITY_UNRESOLVED`. V1.3 must not remove or bypass
that denial. A later V1.3 API version should accept a logical model and request
constraints, then let Jous select a route; it should not reinterpret the frozen
V1.2 request contract.

## Adapter boundary and initial route candidates

V1.2 already has a supplier-neutral `ExecutionRequest`/`Outcome` contract and
an injected adapter seam. Keep that boundary. Existing adapters/gateways should
handle protocol translation, bounded retries only if a later contract permits
them, timeout/error normalization, and server-side credential use. Jous remains
the authority for route admission, prices, complete effective-cost calculation,
ranking, selection, and immutable decision evidence. Portkey and LiteLLM Core
are both deferred: neither is needed to deliver this economic slice, and adding
either now would add another provider abstraction/deployment without a proven
protocol bottleneck. Do not put both in series.

The initial catalog may represent these as candidate route versions for
`jous.text.general.v1` / the Qwen3-32B reference:

| Candidate | Shape | V1.3A state |
| --- | --- | --- |
| Direct DeepInfra | direct provider | candidate; dispatch disabled |
| OpenRouter to pinned DeepInfra | gateway with pinned provider | candidate; dispatch disabled |
| Vercel AI Gateway to pinned DeepInfra | gateway with pinned provider | candidate; dispatch disabled |
| Existing HF to DeepInfra | existing V1.2 route | preserved, admission denied |

These are catalog design candidates, not verified operational capabilities or
current account prices. In particular, a gateway that can choose a provider
dynamically stays economically ineligible unless Jous holds an approved,
complete provider/price outcome envelope for that exact route version. V1.3A
does not activate any candidate.

## Domain contract implemented for review

`services/api/src/jous_api/route_economics.py` defines immutable
`LogicalModelVersion`, `RouteVersion`, `PricingVersion`, `RouteEvaluation`,
and `RouteDecision` values. It has no database, network, provider, credential,
or dispatch dependency. Operational/admission eligibility and economic
eligibility are represented independently; overall eligibility requires both.

The first logical reference is `jous.text.general.v1`, with a versioned
text-generation capability contract. Model, route, and price status are
server-owned facts. `RouteVersion` distinguishes direct routes from gateways,
records a pinned provider or a separately evidenced dynamic-provider envelope,
and keeps service tier explicit. Dynamic gateway selection is economically
ineligible without an authorized complete price envelope. The frozen HF route
is not re-enabled by this module.

### Money and validity

Prices are exact nonnegative `Decimal` values, in USD, per million tokens.
Binary floats are rejected. Source rates are limited to twelve fractional
decimal places; serialization removes insignificant trailing zeroes, never
rounds, and never emits exponent notation. Cost arithmetic uses a local
50-digit decimal context. Persisted estimates should use the exact canonical
decimal string and digest the canonical decision JSON.

A price can be used only when its status is approved and
`effective_from <= decision_time < valid_until`. Missing, pending/withdrawn,
expired, not-yet-effective, tier-mismatched, or incomplete billing evidence is
not eligible. An unknown provider or gateway request fee is `None`, not zero.
Verified zero is represented by an explicit decimal zero and a verified fee
basis. Account-funding/payment fees are not folded into per-request cost; V1.4
may account for them separately.

For V1.3A text routes the pure cost function is:

```text
(input_token_bound * input_price_per_1m
 + output_allowance * output_price_per_1m) / 1_000_000
 + verified_provider_request_fee
 + verified_gateway_request_fee
```

This is an estimated maximum supplier/route cost. It is not a customer price,
realized provider cost, realized savings, Jous revenue, or reward value.

### Evaluation and deterministic choice

Stable reason codes distinguish route disabled/admission denied, capability or
context mismatch, unresolved token authority, missing/unverified/expired
pricing, unsupported currency, and unresolved billing basis. No raw upstream
error becomes a reason code. At most 64 candidates are evaluated. Candidate
evidence is sorted by immutable route ID/version, uses stable reason ordering,
and canonical JSON is bounded to 65,536 bytes.

Among overall eligible candidates, exact Decimal cost sorts ascending and
immutable `route_id` breaks exact ties ascending. There is no randomized,
provider-preference, or LLM-based selection. No eligible candidate produces a
decision with no selected route and `NO_ELIGIBLE_ROUTE`; the later dispatcher
must treat that as a hard no-dispatch result. Selection itself is not yet wired
to the V1.2 execution service.

## Proposed PostgreSQL schema — superseded by the adjudication addendum below

Four tables are justified for the intended persistent system: a logical model
authority, versioned route authority, immutable price versions, and a
task-bound decision snapshot. `route_catalog` could embed model fields, but
that would duplicate logical identity and capability authority across every
route. Separate candidate rows are not needed for v0 because bounded candidate
evaluations are captured in the immutable decision snapshot.

The following is a schema contract for CTO review, not executable migration
SQL. It shows key columns and constraints; all relations are in `public`.

```sql
CREATE TABLE public.model_catalog (
    logical_model_id text NOT NULL,
    model_version integer NOT NULL CHECK (model_version > 0),
    display_name text NOT NULL CHECK (length(btrim(display_name)) BETWEEN 1 AND 128),
    modality text NOT NULL CHECK (modality = 'text_generation'),
    required_capabilities text[] NOT NULL,
    context_capacity integer NOT NULL CHECK (context_capacity > 0),
    max_output_allowance integer NOT NULL,
    authority_status text NOT NULL CHECK (authority_status IN ('candidate','approved','retired')),
    authority_evidence_id text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT statement_timestamp(),
    PRIMARY KEY (logical_model_id, model_version),
    CHECK (max_output_allowance > 0 AND max_output_allowance <= context_capacity),
    CHECK (cardinality(required_capabilities) <= 32)
);

CREATE TABLE public.route_catalog (
    route_id text NOT NULL,
    route_version integer NOT NULL CHECK (route_version > 0),
    logical_model_id text NOT NULL,
    logical_model_version integer NOT NULL,
    supplier_id text NOT NULL,
    supplier_native_model_id text NOT NULL,
    underlying_provider text,
    route_kind text NOT NULL CHECK (route_kind IN ('direct','gateway')),
    gateway_id text,
    provider_selection text NOT NULL CHECK (provider_selection IN ('direct','pinned','dynamic')),
    service_tier text NOT NULL,
    capabilities text[] NOT NULL,
    context_capacity integer NOT NULL CHECK (context_capacity > 0),
    operational_enabled boolean NOT NULL DEFAULT false,
    admission_authorized boolean NOT NULL DEFAULT false,
    token_authority_status text NOT NULL CHECK (token_authority_status IN ('verified','unresolved')),
    dynamic_provider_envelope_authorized boolean NOT NULL DEFAULT false,
    dynamic_provider_envelope_id text,
    route_authority_id text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT statement_timestamp(),
    PRIMARY KEY (route_id, route_version),
    FOREIGN KEY (logical_model_id, logical_model_version)
        REFERENCES public.model_catalog (logical_model_id, model_version) ON DELETE RESTRICT,
    CHECK (cardinality(capabilities) <= 32),
    CHECK (
      (route_kind = 'direct' AND gateway_id IS NULL AND provider_selection = 'direct' AND underlying_provider IS NOT NULL)
      OR
      (route_kind = 'gateway' AND gateway_id IS NOT NULL AND provider_selection IN ('pinned','dynamic'))
    ),
    CHECK (provider_selection <> 'pinned' OR underlying_provider IS NOT NULL),
    CHECK (NOT dynamic_provider_envelope_authorized OR dynamic_provider_envelope_id IS NOT NULL)
);
CREATE INDEX ix_route_catalog_model_enabled
    ON public.route_catalog (logical_model_id, logical_model_version, operational_enabled, route_id);

CREATE TABLE public.route_pricing_versions (
    pricing_version_id uuid PRIMARY KEY,
    route_id text NOT NULL,
    route_version integer NOT NULL,
    service_tier text NOT NULL,
    currency char(3) NOT NULL CHECK (currency = 'USD'),
    input_price_per_1m numeric(20,12) NOT NULL CHECK (input_price_per_1m >= 0),
    output_price_per_1m numeric(20,12) NOT NULL CHECK (output_price_per_1m >= 0),
    provider_request_fee_usd numeric(20,12),
    gateway_request_fee_usd numeric(20,12),
    fee_basis_verified boolean NOT NULL,
    source_type text NOT NULL CHECK (source_type IN ('provider_published','gateway_published','invoice_review','manual_review')),
    source_evidence_id text NOT NULL,
    evidence_sha256 bytea,
    reviewed_at timestamptz NOT NULL,
    effective_from timestamptz NOT NULL,
    valid_until timestamptz NOT NULL,
    pricing_status text NOT NULL CHECK (pricing_status IN ('pending','approved','withdrawn')),
    created_at timestamptz NOT NULL DEFAULT statement_timestamp(),
    FOREIGN KEY (route_id, route_version)
        REFERENCES public.route_catalog (route_id, route_version) ON DELETE RESTRICT,
    UNIQUE (pricing_version_id, route_id, route_version),
    CHECK (valid_until > effective_from),
    CHECK (provider_request_fee_usd IS NULL OR provider_request_fee_usd >= 0),
    CHECK (gateway_request_fee_usd IS NULL OR gateway_request_fee_usd >= 0),
    CHECK (pricing_status <> 'approved' OR
           (fee_basis_verified AND provider_request_fee_usd IS NOT NULL AND gateway_request_fee_usd IS NOT NULL)),
    CHECK (evidence_sha256 IS NULL OR octet_length(evidence_sha256) = 32)
);
CREATE INDEX ix_route_pricing_current
    ON public.route_pricing_versions (route_id, route_version, pricing_status, effective_from, valid_until);

CREATE TABLE public.route_decisions (
    decision_id uuid PRIMARY KEY,
    task_id uuid NOT NULL UNIQUE,
    organization_id uuid NOT NULL,
    project_id uuid NOT NULL,
    actor_user_id uuid NOT NULL,
    dispatch_claim_id uuid NOT NULL,
    decision_version text NOT NULL,
    selector_version text NOT NULL,
    logical_model_id text NOT NULL,
    logical_model_version integer NOT NULL,
    selected_route_id text,
    selected_route_version integer,
    selected_pricing_version_id uuid,
    decision_status text NOT NULL CHECK (decision_status IN ('selected','no_eligible_route')),
    decided_at timestamptz NOT NULL,
    currency char(3) NOT NULL CHECK (currency = 'USD'),
    input_token_bound integer NOT NULL CHECK (input_token_bound >= 0),
    output_allowance integer NOT NULL CHECK (output_allowance >= 0),
    estimated_cost_usd numeric(38,24),
    candidate_evaluations jsonb NOT NULL,
    selection_rationale text[] NOT NULL,
    snapshot_sha256 bytea NOT NULL CHECK (octet_length(snapshot_sha256) = 32),
    created_at timestamptz NOT NULL DEFAULT statement_timestamp(),
    FOREIGN KEY (task_id, organization_id, project_id, actor_user_id, dispatch_claim_id)
        REFERENCES public.tasks (id, organization_id, project_id, actor_user_id, dispatch_claim_id) ON DELETE RESTRICT,
    FOREIGN KEY (logical_model_id, logical_model_version)
        REFERENCES public.model_catalog (logical_model_id, model_version) ON DELETE RESTRICT,
    FOREIGN KEY (selected_route_id, selected_route_version)
        REFERENCES public.route_catalog (route_id, route_version) ON DELETE RESTRICT,
    FOREIGN KEY (selected_pricing_version_id, selected_route_id, selected_route_version)
        REFERENCES public.route_pricing_versions (pricing_version_id, route_id, route_version) ON DELETE RESTRICT,
    CHECK (jsonb_typeof(candidate_evaluations) = 'array'
           AND jsonb_array_length(candidate_evaluations) <= 64
           AND pg_column_size(candidate_evaluations) <= 65536),
    CHECK (cardinality(selection_rationale) <= 16),
    CHECK (estimated_cost_usd IS NULL OR estimated_cost_usd >= 0),
    CHECK (
      (decision_status = 'selected' AND selected_route_id IS NOT NULL
       AND selected_route_version IS NOT NULL AND selected_pricing_version_id IS NOT NULL
       AND estimated_cost_usd IS NOT NULL)
      OR
      (decision_status = 'no_eligible_route' AND selected_route_id IS NULL
       AND selected_route_version IS NULL AND selected_pricing_version_id IS NULL
       AND estimated_cost_usd IS NULL)
    )
);
CREATE INDEX ix_route_decisions_project_time
    ON public.route_decisions (organization_id, project_id, created_at DESC, decision_id);
```

### Ownership, privileges, RLS, and immutability proposal

- **Owner:** the existing migration/database owner (currently `postgres` on
  managed Dev); ownership never moves to runtime roles.
- **Global catalogs:** `model_catalog`, `route_catalog`, and
  `route_pricing_versions` are Jous-global, not tenant-owned. Enable and FORCE
  RLS. A narrow `jous_runtime` SELECT policy may expose only reviewed
  non-secret catalog rows; runtime has column-level SELECT only. No runtime
  INSERT/UPDATE/DELETE or relation-level ACL. `jous_security_reader` and
  Supabase API roles receive no catalog privileges unless separately justified
  by an explicit contract.
- **Decision:** `route_decisions` is tenant/project/task-bound by its composite
  task FK and RLS checks. Enable and FORCE RLS. Its read policy must match the
  task’s authenticated project-access boundary; its insert policy must enforce
  exact task, organization, project, actor, and dispatch-claim binding. Runtime
  receives column-level SELECT and narrowly enumerated INSERT only; no UPDATE,
  DELETE, or grant option. No relation-level ACL entries are introduced.
- **History:** catalog and pricing changes append a new version. Runtime cannot
  update or delete historical rows. Decision rows are immutable to runtime;
  retaining exact candidate/pricing snapshots makes later reconciliation
  independent of current catalog values.
- **No secrets:** provider credentials and gateway API keys remain in the
  server’s secret configuration. They are never stored in these tables or
  returned through the API.

These policies/grants are schema-contract requirements only. They are not
implemented in V1.3A and must be integrated with the frozen runtime validator
and reviewed in a future authorized migration design.

Each alternative should expose its bounded Jous route identity, eligibility,

not realized savings, revenue, customer charge, or reward value. The UI can
show “Routing decision”, selected route, alternatives, estimated maximum cost,
and why it qualified, without depending on Portkey/LiteLLM fields. No API or UI
change is part of V1.3A.

## Step 2 adjudication addendum — candidate only

This addendum supersedes the four-table proposal above. The Step 2 source
review recommends three tables, with no model_catalog or route_catalog:

- Source owns logical model versions, approved route identities, supplier and
  provider mapping, capabilities, route kind, operational activation,
  admission, and token/template authority. A database row never activates a
  route. The runtime matches pricing identities against this source registry.
- PostgreSQL stores route_pricing_versions, route_pricing_revocations, and
  route_decisions. Prices are exact reviewed historical facts; withdrawal is
  a separate append-only fact; decisions are tenant-bound evidence.
- Approved price windows are half-open [effective_from, valid_until). A
  same-key approved overlap is rejected under a transaction advisory lock in
  a narrow PostgreSQL trigger; no extension is proposed. Pending evidence
  does not participate. Revocation immediately removes a price from new
  runtime reads without rewriting the historical price row.
- Decisions are exactly one per V1.2 task/dispatch claim and reuse the
  non-deferrable RESTRICT composite FK to tasks over task, organization,
  project, actor, and dispatch_claim_id. The table uses ENABLE/FORCE RLS and
  task-backed SELECT/INSERT policies. The future transaction commits claim
  and decision before releasing the connection for provider I/O.
- Only a selected, overall-eligible decision is persisted with a task claim.
  A no-eligible-route result is fail-closed before claim creation and may be
  returned as an API result, but it creates neither a task nor a decision row.
- All new relations remain postgres-owned and owner-only at relation level.
  Runtime gets column SELECT on price rows, SELECT of the price ID needed to
  enforce revocation filtering, and column SELECT/INSERT on decisions except
  created_at. Runtime cannot mutate price or revocation authority, update or
  delete decisions, or receive forbidden privileges. Security reader, PUBLIC,
  anon, authenticated, and service_role receive none.
- Candidate migration ID is 0005_route_economics (20 characters), parent
  0004_product_acl_hardening. The future transactional migration creates the
  three tables, overlap trigger, RLS/policies, grants, dynamic owner-only ACL
  cleanup, and exact postcondition checks. Downgrade is no-op. No migration
  exists or is authorized by this design review.

The exact column, type, constraint, index, FK, and privilege contract is in
the Step 2 review report. This remains an unapproved, non-migrated candidate;
V1.1/V1.2 and the non-dispatching boundary remain unchanged.

## Step 3 local implementation status (2026-11-19)

**DESIGNED / APPROVED:** the three-object hybrid from the Step 2 adjudication:
source-owned model/route/admission authority; PostgreSQL-owned reviewed price
versions, append-only price revocations, and immutable task-bound decisions.
No model or route catalog is introduced. A price row can never activate a
provider route.

**IMPLEMENTED LOCALLY, NOT MIGRATED:** `0005_route_economics` adds exactly
`route_pricing_versions`, `route_pricing_revocations`, and `route_decisions`.
All are postgres-owned by migration precondition, ENABLE/FORCE RLS, and have
owner-only relation ACLs after dynamic relation and column ACL cleanup. Runtime
gets column SELECT on pricing, pricing-version-ID-only SELECT on revocations,
and column SELECT/INSERT on decisions (excluding `created_at`). Pricing and
revocations have no runtime write privileges. Decisions use the V1.2
non-deferrable composite task/organization/project/actor/claim FK and one row
per task and dispatch claim. Their canonical snapshot remains bounded TEXT;
the database checks its JSON object shape and SHA-256 over the exact UTF-8
bytes.

Fee applicability is explicit. Each applicable component requires a known
nonnegative amount for approval; a reviewed zero is stored as numeric zero.
A non-applicable provider/gateway component is represented by its applicability
flag and NULL amount, so it is not given a fictitious economic meaning. An
approved version requires verified fee-basis evidence. The historical
OpenRouter account-funding fee is not converted into a request fee.

Approved intervals are half-open. A trigger serializes the complete price
identity with a deterministic PostgreSQL advisory transaction lock and rejects
overlap; adjacent boundaries are accepted. A revocation is a separate append
record and immediately removes the price from runtime price reads without
changing the historical price row. Runtime cannot write either authority
table. The database owner remains privileged; append-only means immutable to
the runtime role and controlled maintenance, not immutable to postgres.

The local SQL contract is normalized as follows. `route_pricing_versions`
stores the composite source route identity (`route_id`, `route_version`,
`service_tier`, USD `currency`, and fixed `billing_basis`), exact
`numeric(20,12)` input/output rates, independent provider/gateway fee
applicability flags and optional amounts, fee verification, source/evidence
reference, review/effective interval, `pending|approved` status, and creation
time. Approved status requires a verified basis and an explicit amount for
every applicable fee; zero is a real numeric zero, while a non-applicable fee
has NULL amount. Pending evidence may preserve an unresolved applicable fee.
The table has primary and composite unique keys, bounded/source/status/rate/
interval checks, and lookup/evidence indexes.

`route_pricing_revocations` has one row per pricing version, with append-only
revocation time, reason code, and evidence reference; its FK is RESTRICT and
non-deferrable. `route_decisions` has `task_id` as primary key and a unique
dispatch claim, the exact tenant/task/actor/claim tuple, decision/selector/model
versions and time, selected route and price identity, token bounds, estimated
maximum USD supplier/route cost, canonical JSON TEXT, exact-byte SHA-256, and
creation time. It has composite RESTRICT/non-deferrable FKs to V1.2 tasks and
the exact selected pricing identity; bounds and snapshot-to-column consistency
are database checked. No no-route decision is persisted.

The successor validator composes after the unchanged V1.2 validator. It checks
the new revision, table/column/constraint/index/owner/RLS contracts, key/FK
shape, policies, ACLs, privileges, overlap-trigger identity, and source-route
identity compatibility. CHECK expressions compare exact token sequences and
policy expressions compare whitespace-normalized source only; neither removes
operators, casts, parentheses, or clauses. PostgreSQL catalog rendering has not
yet been calibrated, so a deparse difference deliberately fails closed.
